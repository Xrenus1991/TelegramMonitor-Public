# Ограниченный поиск Unicode-вариантов — выпуск-кандидат

**Состояние:** код и UI подготовлены в отдельной ветке, без автоматического развёртывания. Результаты CI и stage фиксируются отдельно, после успешного прогона. Production не изменять до backup/restore/rollback и отдельного read-only smoke.

## Что делает

- Защищённая Basic Auth ручная команда `GET /api/text/search-variants?q=...&source_id=...`.
- PostgreSQL возвращает **не более 101 последнего кандидата** по `timestamp DESC, key DESC`, в ответ идут результаты проверки максимум **100**. `source_id` и `before` ограничивают выборку ДО проверки, а не после неё. Даты принимаются с явным часовым поясом.
- Каждое сообщение читается не более чем в первых 4001 символе; анализируется до 4000. В исходную базу ничего не записывается: неизменны `text`, `summary`, `sender_user_id`, `score`, `checkpoint`.
- Используется консервативный `ru-context-v1` и словарь проверенных русских слов, без OpenAI. URL/email/@username/армянские слова сохраняются согласно ограничениям текущего нормализатора.
- Ответ выдаёт `key`, `matched_on`, `version`, `scanned`, `candidate_limit`, `candidate_truncated`, `text_truncated`, `scope=latest_candidate_window` и `persisted=false`. Это **не поиск по всей истории** и не доказательство намерения или события.
- UI: отдельная форма с запросом и необязательным положительным числовым ID группы, явно показывает усечение выборки/длинных сообщений; карточка по результату открывает отдельную ручную проверку исходного фрагмента с существующим защищённым `/api/text/variants`.

## Включение и безопасность

**Новый отдельный opt-in** `CLOUD_VARIANT_SEARCH_ENABLED=true` включает только этот endpoint. По умолчанию выключен (HTTP 503), даже когда существующая `CLOUD_TEXT_VARIANTS_ENABLED=true` разрешает инспекцию отдельного сообщения. Без Basic Auth ответ HTTP 401. Без рабочего Unicode backend ответ HTTP 503.

Включать флаг только после тестов на изолированной базе PostgreSQL и браузерной проверки. Не добавлять новые Telegram-сессии, не делать платные запросы, не повышать уровень угрозы автоматически, не открывать dashboard в публичный Интернет.

## Доказательства готовности перед production

1. `tests/test_variant_search.py`, `tests/test_variant_search_api.py`, `tests/test_variant_search_postgres.py` — выключенная функция, авторизация, limit, фильтр source/time, read-only PostgreSQL, сохранность оригиналов, длинные тексты.
2. `scripts/check_variant_search_ui.py` — Chromium mock API: ручной запуск, ID фильтр, тексты как безопасные text nodes, предупреждения, ошибки отключённой функции.
3. Проверка CI `.github/workflows/variant-search-postgres.yml` и общая регрессия `offline-tests.yml`; отдельно следить за пропущенными тестами.
4. Изолированный stage на восстановленной копии production PostgreSQL **только чтение**, без второго Telegram Collector. Измерить задержку и ресурсы 100x4000 символов.
5. Перед выпуском свежий backup + проверенный restore, закреплённые IDs/образы, конкретный rollback dashboard. Потом точечный authenticated read-only production smoke; новый флаг включать только после готовности отката.

## Не входит

Полнотекстовый индекс по всей истории, постоянное хранение нормализованного текста, автоматическая классификация, массовый поиск по всем источникам, индексация медиа и распознавание личности. Для этого нужны отдельные дизайн/ресурсные тесты.
