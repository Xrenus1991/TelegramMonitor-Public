# Определение языка и перевод: адаптер этапа 2

Состояние: ручной API/UI из PR33/34 установлен в production 06.11.2026; PR35 подключил опциональный HTTP-контроль8097 к прежним правилам восстановления. Массовая рабочая очередь перевода не подключена.

Модуль telegram_monitor.cloud.language_translation предоставляет TranslationService.
Он выключен по умолчанию (enabled=False), принимает только непустой текст до3000символов,
возвращает отдельно original_text и translated_text, код языка, статус и версию.
Оригинал не нормализуется и не перезаписывается. RU возвращается без внешнего вызова.
Lingua2.2.0 закреплена в optional extra translation, Apache2.0. Политика ограничена
RU/HY/EN; короткие и выраженно смешанные тексты могут быть unknown, без платного вызова.
Оценка качества на реальной переписке пока не проведена.

Для en/hy→ru используется уже существующий backend и paid_call:
модель, общий месячный предел и ledger берутся из существующей конфигурации.
Новых ключей, аккаунтов и лимитов нет. Один запрос, без автоматических retries,
общий timeout100s; output_limit=min(1000,cfg.max_output_tokens).
Содержимое помечается недоверенными данными. Перевод — производный текст, не
подтверждение достоверности сообщения, личности или фактов.

TranslationCache хранит перевод отдельно в tm_text_translations. Ключ включает
SHA256 точного оригинала, source/target, model, версию адаптера и detector policy.
Конструкторы ничего не создают; create_schema вызывается только отдельной
проверенной процедурой подготовки. Основная таблица messages не меняется.
Уникальный pending claim предотвращает параллельную оплату одного ключа.
После транспортной ошибки/отмены/невалидного результата claim становится failed;
автоматического повторного платного запроса нет. После crash pending остаётся busy.
Оператор должен сверить ledger перед будущей отдельной процедурой восстановления.
Это ограничение предотвращает скрытое повторное списание, но пока требует ручного
разбора ошибочных claims. Отказ резервирования не отправляет запрос и удаляет
только собственный неоплаченный claim, позволяя повтор после разрешения бюджета.

## Проверки и подключение

Unit-тесты проверяют оригинал, кэш, версии ключа, disabled/dry_run/unknown/RU,
размер, отказ бюджета, реальное резервирование/settlement на synthetic ledger,
ошибки/отмену и перекрывающиеся вызовы.
scripts/check_translation_stage.py допускает только пустую выделенную БД
tm_translation_stage с пользователем stage на loopback/postgres и синтетическим backend.
Проверяет настоящий Lingua и PostgreSQL: четыре одновременных claim, один владелец,
cache hit, RU/unknown без оплаты, отказ бюджета и отсутствие записи messages.
Внешний перевод и Telegram в этом прогоне не вызываются.

Следующее подключение: authenticated on-demand API/UI, явное включение, отдельный
путь записи производных данных через существующий разрешённый worker, обработка
failed/busy без повторного списания. Нельзя выдавать dashboard новые DB-права или
API-ключи как побочный эффект. Массовый автоматический перевод пока не подключён.

До production: сверить runtime, сохранить образы/конфигурацию, свежий проверенный
backup, проверить точный кандидат на изолированной копии и отрепетировать конкретный
откат приложения. Таблица производных данных может остаться неиспользуемой при
откате; удаление рабочей БД/данных и восстановление старого дампа не требуется.
Этот документ не является исполнимым откатом и не разрешает обход release-проверок.


## Ручной API/UI (LANG-02)

POST /api/text/translate принимает только key существующего сообщения. Весь router
подключён под существующий authorize; POST требует same-origin JSON и X-TM-Action.
GET /api/text/translation-authorize проверяет тот же HTTP Basic без обращения к БД.
Внутренний worker endpoint проверяет доступ callback-запросом к этому фиксированному
адресу dashboard. Authorization существует только в памяти запроса, не сохраняется
в worker env/таблицы/логи. Redirect и environment proxies запрещены.
Worker читает оригинал сам; dashboard сохраняет SELECT-only подключение.
Основная классификация и HTTP работают на одном asyncio-loop; существующие budget,
model и paid_call разделяются. Для долгих запросов действует один HTTP-slot; запросы
не запускаются автоматически при открытии страницы. В UI выводятся текстовые узлы,
оригинал и перевод отдельно, unknown/busy/failed/budget statuses.

Настройка CLOUD_TRANSLATION_ENABLED нужна в обоих проверенных контейнерах при
конкретном выпуске; код по умолчанию выключен. Port8097 — только внутренняя Docker
сеть, публикация на хост не предусмотрена. Готовый production compose здесь не
предлагается: фактическая конфигурация должна быть сохранена и воспроизведена.

Доказательства: PR34 и docs/reports/TRANSLATION_API_UI_STAGE_20261106_RU.md.

См. docs/reports/TRANSLATION_PRODUCTION_20261106_RU.md: точные worker/dashboard образы, изолированная восстановленная БД, real provider EN→RU/cache и productionbrowser. Лимиты$5/месяц и deep3/сутки сохранены. Rollback данного выпуска: /var/lib/tm-actions/monitor-autonomy/deployments/translation-20261106T071241Z/rollback.sh . Предыдущие приложения сохранены; рабочая БД при возврате не восстанавливается из старого дампа. Фактический cron09:22UTC/13:22Армения проверил8097HTTP200.

Статус failed/busy после неопределённого результата не запускает повторную оплату автоматически; механизм безопасного reconciliation и расширенный корпус качества остаются в плане. Один реальный перевод не является оценкой общего качества на переписке.
