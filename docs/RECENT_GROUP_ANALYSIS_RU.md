# Ручной анализ последних N сообщений выбранной группы

## Поведение

В Dashboard рядом с кнопкой «Отключить мониторинг» отображаются числовое поле
«Последние» (1–1000, по умолчанию 50) и кнопка «Анализировать» для **явно включённых**
групп и каналов. Для каждой группы оператор задаёт количество **последних Telegram
сообщений**, которое будет запрошено **один раз**. В том числе можно досканировать
историю уже подключённой группы без сброса её checkpoint.

При нажатии Dashboard записывает заявку в `tm_source_recent_requests` с
`status=pending` и возвращает HTTP 202. Collector не чаще двух заявок за цикл
берёт `pending` (либо `running`, если занятие устарело на 20 минут), читает
до N последних Telegram-сообщений и сохраняет **только отсутствующие** записи
через `Store.ingest(..., advance_checkpoint=False)`. Worker обрабатывает их
обычным путём с существующим бюджетом, лимитами и очередью. Уже сохранённые
сообщения не переписываются, а ранее классифицированные **не проходят повторный
анализ** и не создают повторные запросы OpenAI.

Статусы в UI: `pending` — в ожидании Collector; `running` — загрузка;
`done` — запрос/досканирование завершены, отображаются число увиденных и
число новых сообщений, поставленных в очередь; `failed` — ошибка с возможностью
нового запуска. Статус `done` **не означает**, что OpenAI завершил анализ;
состояние классификации смотрится в общей очереди. Весь обычный мониторинг
продолжает работать независимо.

## Ограничения безопасности

- По умолчанию `CLOUD_SOURCE_RECENT_ENABLED=false`: ни UI, ни POST не запускаются
  до миграции и верификации ролей; Collector не читает очередь заявок.
- Только статус `approved` может создавать запросы; отключённые/ушедшие
  группы не читаются. Только один активный запрос на группу и максимум десять
  одновременно по всем группам. Максимум 1000 сообщений за запрос.
- API требует HTTP Basic, same-origin JSON + заголовок `X-TM-Action: 1`.
- Исторические сообщения могут попадать в очередь только при ручном действии,
  без автоматического массового backfill после обновления.
- Никаких новых Telegram-сессий и отправки сообщений от имени пользователя.
- Новая таблица не разрешает контроллеру изменять `messages`, `checkpoints`
  или уже сохранённые решения о мониторинге.

## Миграция PostgreSQL

**Не применять на рабочем сервере без свежего бэкапа с изолированной проверкой
восстановления и успешного stage.** Файл `sql/source_recent_requests.sql`
создаёт только новую таблицу и два индекса; существующие сообщения не изменяются.

Требуются роли, которые действительно используются текущими контейнерами:
- `reader_role` — Dashboard, только SELECT из новой таблицы;
- `controller_role` — отдельный Dashboard-контроллер, SELECT(id,peer_id,status)
  и INSERT(id,peer_id,message_count,status,requested_at);
- `collector_role` — Collector, SELECT/INSERT/UPDATE для управления заявками.

Выполнять миграцию под администратором PostgreSQL через psql с
`-v ON_ERROR_STOP=1`, `-v reader_role=...`, `-v controller_role=...`,
`-v collector_role=...`, SQL-файл передавать через stdin/файл. Роли не
определять по догадкам. Никаких паролей в GitHub Actions логи. Проверить через
`has_column_privilege` и отдельные подсоединения под каждой ролью:
контроллер не имеет SELECT/UPDATE на `messages`; Dashboard не умеет INSERT;
Collector может завершить заявку; существующие маршруты Dashboard работают.

Сначала обновить Dashboard и Collector на проверенные образы (один Collector),
оставляя новый флаг выключенным. После проверки ролей/GET/POST в stage включить
`CLOUD_SOURCE_RECENT_ENABLED=true` в окружении обоих сервисов с
предварительным сохранением старых контейнеров для отката. Проверить одну
тестовую группу. При откате выключить оба флага, вернуть образы; новую таблицу
не удалять до оценки незавершённых заявок. Не менять `RentWeeklySender`.

## Известные ограничения

При отсутствии новых записей или если последние N сообщений уже классифицированы,
новые затраты API равны нулю. При повторном нажатии после завершения
запрос может снова опросить Telegram, но дедупликация не поставит прежние
сообщения в очередь. Процесс работает по правам учётной записи Telegram;
закрытые группы, из которых аккаунт вышел, не могут быть запрошены.
