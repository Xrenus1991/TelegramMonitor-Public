# Автономное обслуживание Telegram Monitor с Sherlock

Workflow `.github/workflows/tm-autonomy.yml` находится в main. Расписание GitHub:
каждые 15 минут (минуты 7, 22, 37, 52). Планировщик GitHub может задерживать или
пропускать запуск. Дополнительно установлен локальный crontab пользователя tm-actions
на те же минуты: bin/cron_entry.py в /var/lib/tm-actions/monitor-autonomy.
Он выполняет сохранённую копию autonomy.py --repair независимо от GitHub.
Оба канала используют общие flock/state; циклы в пределах пяти минут не повторяются.
При недоступном сервере локальный контроль не работает.
Исходное приложение по-прежнему обслуживается Docker restart policy.

## Действия

- Проверка четырёх сервисов: tm-dashboard-v861-live-readonly,
  tm-v861-live-collector, tm-v861-live-worker, tm-sherlock-stage.
- HTTP /health должен вернуть 200: dashboard на 8098, Sherlock на 8099.
- PostgreSQL проверяется чтением количества сообщений. Он не перезапускается.
- Collector и worker проверяются на Running и Docker health при наличии. При явно включённом CLOUD_TRANSLATION_ENABLED у worker дополнительно проверяется /health8097 и translation_enabled=true; при выключенной функции этот порт не требуется.
  Это не доказывает отсутствие зависания обработки или доступность Telegram/OpenAI.
- После двух подряд неуспешных проверок возможен restart только одного из этих
  четырёх сервисов. Требуется исправная база; максимум три попытки в сутки на
  сервис, интервал минимум час. Контейнеры paused/restarting/dead не перезапускаются.
- Раз в 24 часа создаются custom pg_dump и дамп ролей. База восстанавливается в
  отдельном контейнере без сети/портов, с ограничениями CPU/RAM, на временном tmpfs.
  После теста временный контейнер удаляется. Роли и права дополнительно проверяются check_roles_restore.py в изолированном PG; проверяется SCRAM-вход существующими credentials без их вывода. При сбое резервирования повторная попытка не чаще 6 часов.
- Рабочая база никогда автоматически не восстанавливается из дампа.
- RentWeeklySender, старые dashboard и тестовые проекты не обслуживаются.

## Состояние и пауза

Файлы хранятся только на сервере: `/var/lib/tm-actions/monitor-autonomy`, каталог
0700. latest.json — безопасный статус; state.json — счётчики и лимиты;
backups/ — дампы, контрольные суммы и отметки проверки. Дампы не загружаются в GitHub.
Автоматического удаления резервных копий нет. При свободном месте менее 1 GiB
резервирование блокируется и задание завершается ошибкой.

Пауза обслуживания: создать `/var/lib/tm-actions/monitor-autonomy/PAUSE` от
tm-actions или root. Продолжить: удалить только этот файл. Также можно отключить
workflow Telegram Monitor autonomy в GitHub Actions, но это не останавливает локальный cron.
PAUSE действует на оба канала. Это не выключает приложение.

## Исправления кода

Этот скрипт не генерирует код и не устанавливает образы/миграции. Для исправления
программных ошибок используется отдельное задание ChatGPT с доступом к GitHub,
если оно успешно создано и включено. Статус задания нужно проверять отдельно.
До любого изменения приложения требуется подтвердить фактический исходный код,
сделать свежую проверенную резервную копию и снимок конфигурации, проверить кандидата
на изолированных данных и подготовить точную процедуру отката приложения.
Универсальный автоматический откат обновлений приложения пока не установлен.
Нельзя подменять рабочий Compose примером из репозитория или автоматически
откатывать рабочую базу, теряя новые сообщения. Не менять лимиты OpenAI,
Telegram-сессии, права доступа или рассылку объявлений без отдельного основания.

Служебные логи содержат только статусы и счётчики. Не печатать env, токены,
команды запуска с встроенными паролями, сообщения Telegram и полные docker logs.
Параллельные задания сериализованы общей concurrency group и локальным flock.

## Локальное расписание

Установка/обновление копий: ops/install_local_schedule.py через maintenance workflow.
Изменение autonomy.py в GitHub само по себе не обновляет локальную копию.
Установщик сохраняет прежний crontab и скрипты в защищённом schedule-before-*.json,
проверяет запись и восстанавливает предыдущее состояние при ошибке установки.
Не удаляет посторонние cron-задания. cron-status.json содержит время и exit code
последнего локального запуска; cron-last.log ограничен по размеру и остаётся на сервере.
После обновления требуется проверить фактический следующий запуск.


## Ежедневное восстановление ролей и SCRAM

ops/check_roles_restore.py выполняется после успешного локального autonomy.py и отдельным шагом GitHub workflow. Успешный результат кэшируется на24часа; после неуспеха повтор не чаще6часов. Общий flock и PAUSE сохраняются, правила рестартов не меняются.
Проверка создаёт свежий database.dump/roles.sql, проверяет SHA256, восстанавливает globals и DB с владельцами/ACL в networknone контейнере256MiB. Сверяет атрибуты/членство/права, выполняет9read/no-row-write проверок и3SCRAMвхода плюсотклонение3неверныхпаролей.
Текущие credentials используются только в памяти серверного процесса и передаются дочернему psql через stdin. Значения не выводятся и не уходят с сервера. Рабочие роли, passwords и pg_hba не меняются: SCRAM hba включается лишь внутри disposable контейнера.
roles-daily-status.json и roles-daily-attempt.json хранят толькобезопаснуюсводку/времена в защищённомROOT. cron-status.json содержит roles_exit_code. Installer сохраняет предыдущие3скрипта иcrontab дляотката.

## Диагностика остановки обработки

Дополнительный read-only запрос с statement_timeout10s считает только агрегаты:
готовые pending старше30минут, отложенные retry, просроченные более5минут claims
классификации/deep, текущий месячный ledger и число deep за UTC-сутки.
При исчерпанном месячном бюджете pending не объявляются зависанием; ожидание deep
при дневном пределе или отключённом deep также не считается зависанием. Давность
последнего поступления сама по себе не вызывает тревогу: новых сообщений в Telegram
могло не быть. Наличие backlog означает необходимость диагностики, не установленную
причину отказа.

Сигнал processing.requires_attention делает результат неуспешным (exit2), но не
повышает failures контейнеров и не вызывает restart. Если инфраструктура исправна,
локальный cron при exit2 продолжает независимый ежедневный role/SCRAM контроль,
сохраняя exit2 в cron-status. При обычном инфраструктурном сбое сохраняется exit1.
Существующие лимиты рестартов, общие flock/PAUSE и пяти-минутная дедупликация циклов
не меняются. Внешние уведомления/новые сервисы не подключаются.
